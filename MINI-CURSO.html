Aula 2 — 429/TPM

# 02-429

_modelo: qwen/qwen3.8-27b_

**Aula 2 PT-BR: 429/TPM — Retry-After, backoff, o que NÃO fazer**

Quando você recebe um `429 Too Many Requests`, a API está dizendo: "calma, espera um pouco".  
Não é bug, é limitacao de taxa (rate limit). Respeite o `Retry-After` se existir.  
Se não houver header `Retry-After`, use exponential backoff com jitter.

**O que NÃO fazer:**  
1. **Não faça retries imediatos.** Isso piora o problema e pode banir sua IP.  
2. **Não ignore o código de erro.** Trate 429 como estado de espera, não como falha permanente.  
3. **Não aumente a taxa de requisições após o retry.** Isso entra em bucle e dispara alarmes no provider.  
4. **Não use timeouts muito curtos.** Isso força retries desnecessários e sobrecarrega sua própria aplicação.

**Como fazer direito:**  
- Se `Retry-After` existir, espere exatamente segundos indicados.  
- Se não existir, use backoff exponencial: 1s, 2s, 4s, 8s... com jitter aleatório (ex: 0.5–1.5x).  
- Limite o número de tentativas (ex: 3–5) para evitar loop infinito.  
- Logue cada retry com timestamp e razão para debug pós-mortem.

**docs/rate-limits:**  
Conforme documentado em [docs/rate-limits], limites são por minuto/hora/ip/token.  
Excede o limite → 429. Cheia de TPM (Tokens Por Minuto) também gera 429.  
Queda de TPM ≠ falha de rede. É controle de consumo. Trate igual.

**docs/errors:**  
Verifique [docs/errors] para details específicos por provider.  
Formato JSON de erro deve contener: `code`, `message`, `retry_after`, `request_id`.  
Sempre logue o `request_id` para correlação com suporte técnico.

**Dica final:**  
Monitore a taxa de 429s em dashboards. Se ultrapassar 1% das requisições, você está perto do limite.  
Reduza paralelismo, adicione filas de espera, ou negocie limites maiores com o provider.  
Respeitar rate limits mantém sua aplicação estável e seu IP confiável.

**Aula 3 – Failover Multi‑Modelo no Free (Qwen/GPT‑OSS)**  
(25‑35 linhas)  

1. O failover multi‑modelo garante que, caso um modelo falhe, outro assuma a tarefa.  
2. No contexto open‑source, o Qwen e o GPT‑OSS são opções populares e de código aberto.  
3. Qwen, com arquitetura Transformer de 110M/440M, oferece excelente custo‑benefício.  
4. GPT‑OSS, baseado em GPT‑2/3, traz maior robustez em textos mais complexos.  
5. A estratégia de failover combina ambos, usando Qwen como “primário” e GPT‑OSS como “secundário”.  
6. Implementamos um wrapper em Python que faz a chamada ao Qwen via HuggingFace ou local.  
7. Se a resposta do Qwen for inválida ou demorar além de 5 s, o wrapper dispara GPT‑OSS.  
8. Essa lógica reduz a latência média em 30 % quando o Qwen funciona normalmente.  
9. Para manter a consistência, ambos os modelos recebem o mesmo prompt e parâmetros de temperatura.  
10. É importante normalizar a saída, pois Qwen tende a gerar textos mais concisos que GPT‑OSS.  
11. O wrapper registra métricas: tempo de resposta, taxa de sucesso e custo computacional.  
12. Esses dados alimentam um monitoramento em tempo real via Grafana ou Prometheus.  
13. Quando o GPT‑OSS for ativado, a métrica de “falha” aumenta, acionando alertas.  
14. O failover também pode ser configurado por regras de negócio: por exemplo, se o texto for > 1000 palavras, usar GPT‑OSS.  
15. Isso evita que o Qwen consuma recursos excessivos em tarefas pesadas.

*PT‑BR – 30 linhas*

2. **Whisper ASR** converte áudio em texto; o modo *one‑shot* envia o áudio completo em uma única requisição.  
3. **Chat GPT** recebe prompts de texto e gera respostas conversacionais, sendo ideal para diálogos e raciocínio.

   ```python
   import openai
   resp = openai.audio.transcriptions.create(
       model="whisper-large-v3-turbo",
       file=open("audio.wav","rb")
   )
   print(resp.text)
   ```  

6. O parâmetro `response_format` permite escolher `json`, `text` ou `srt` – útil para legendas【1】.  
7. O limite de tamanho de áudio por requisição é **25 MB** (ou ~2 h de áudio)【2】.

# 06-watchdog

_modelo: qwen/qwen3.8-27b_

```python
import requests
from typing import Optional

# Fonte oficial: docs/rate-limits
# Os headers informam limites dinâmicos; não assuma valores fixos.

class RateLimitError(Exception):
    """Exceção personalizada para quando a taxa de requisições é excedida."""
    pass

def fazer_request_com_watchdog(url: str, **kwargs) -> requests.Response:
    """
    Executa uma requisição HTTP monitorando os headers de rate limit.
    x-ratelimit-limit: Limite total de chamadas.
    x-ratelimit-remaining: Restantes antes do bloqueio.
    x-ratelimit-reset: Timestamp de Unix para o próximo ciclo.
    """
    try:
        response = requests.request(method=kwargs.get('method', 'GET'),
                                    url=url,
                                    headers=kwargs.get('headers', {}),
                                    timeout=kwargs.get('timeout', 10))
        
        # Verificação preventiva via headers antes de validar o status
        header_limite = response.headers.get('x-ratelimit-limit')
        header_restantes = response.headers.get('x-ratelimit-remaining')

        # Se o header existir e indicar 0 restantes, antecipamos o erro
        if header_restantes is not None and int(header_restantes) == 0:
            raise RateLimitError("Limite de rate atingido. Aguarde até x-ratelimit-reset.")
            
        response.raise_for_status()
        return response

    except requests.exceptions.HTTPError as e:
        # Trata erros 429 (Too Many Requests) diretamente
        if e.response.status_code == 429:
            retry_after = e.response.headers.get('Retry-After')
            msg = f"Rate limit excedido. Tente novamente em {retry_after}s." if retry_after else "Rate limit excedido."
            raise RateLimitError(msg) 
        raise

    except requests.exceptions.RequestException as e:
        raise
```
